## First run — 332 s, 6 / 7, one real defect

```
01 DOCKER      v29.6.1                          OK
02 PORTS       5 free                           OK
03 SECRETS     .env 0600, salt 64 hex           OK
04 STACK       clickhouse grafana collector     OK
05 CLICKHOUSE  ping ok on 8124                  OK
06 GRAFANA     no health answer on 3001         WAIT
   cause: No healthy answer from 127.0.0.1:3001/api/health: Get "...": EOF
07 COLLECTOR   accepting on 4319                OK
6 / 7 steps complete
```

**Root cause.** Grafana installs bundled plugins on first boot and does not answer `/api/health`
until it finishes; `docker compose up --wait` returns earlier because only ClickHouse declares a
healthcheck. The engine waited 2 s for Grafana and 2 s for ClickHouse, so a healthy install was
reported as failed. `/api/health` answered 200 with `{"database":"ok"}` about 60 s later.

**Fix applied.**
- `stepClickHouse` and `stepGrafana` wait with `Options.Wait` instead of 2 s.
- default `Options.Wait` 90 s → 5 min (cold pulls and plugin installs are slow, and the number is a
  backstop, not a target).
- **Second run: 7 / 7 in 2.0 s**, `.env kept, salt unchanged`, stack reported `already running`.

## Ingestion

| Probe | Result |
|---|---|
| OTLP/HTTP JSON to `127.0.0.1:4319/v1/logs` | 200 `{"partialSuccess":{}}` |
| Hook POST to `127.0.0.1:8089/v1/hooks` | 200 |
| `cardo.bronze_otel_logs` after ~10 s | 1 |
| `cardo.bronze_hook_events` after ~10 s | 1 |

**Timing matters.** The exporter batches with `flush_timeout: 10s`; a read-back that queries
immediately after a 200 sees nothing. The read-back step (Phase 3) must poll for 15–30 s and report
the numbers it actually read.

## Deviations found

1. **Readiness window too short** — fixed (see above). Severity: high, it fails a healthy install.
2. **The collector writes no logs of its own** — `docker logs cardo-collector-1` is empty, even
   though `deploy/collector/config.yaml` promises a REFUSED line for a bad salt. Copy that tells the
   operator to read collector logs is therefore misleading; the collector failure text now points at
   `CARDO_SALT` and the port instead. Upstream documentation defect, worth an issue.
3. **Step 07 proves only that something listens on 4319** — it does not prove a batch is accepted.
   This is the gap the read-back step closes.
4. **`cardo:dev` is built from the repository** during the first run (about 4 minutes on this host).
   Expected, but it is the longest part of a cold install and should be named in the UI estimate.
5. **`/api/login` is not the authentication route on Grafana 12** — no action, recorded so the next
   person does not repeat the wrong test.

## Correction: synthetic probes polluted the session model

Repeated installer runs left 19 rows in each bronze table, and `silver_session` — which groups bronze
by `session_id` with no filter of its own — reported 19 sessions that no person ever ran. Two changes
followed:

- `cardo probe` deletes both rows by marker after a successful read-back, and says so in its value;
  the existing rows were removed and `silver_session` is back to zero probe rows.
- The proof of an installation is now the engineer's own session (`cardo session`, tagged `Proof` in
  the rail). `cardo check` reports it as a seventh row and `cardo check --proof` fails without it.

## E2E: the Admin API path, emulated

`CARDO_E2E=1 go test ./test -run TestE2EAdminPath -v` runs the whole path against the live stack: a
stand-in API serving `test/fixtures/console/single-page.json` retagged to a test organization and
yesterday, the real `poll.Runner`, the real ClickHouse store, and the board's `GET /api/admin`.

It asserts: the poller sends `x-api-key`; one record lands in `bronze_actor_day`; the stored
`pseudonym` carries no email; `silver_actor_day` has the actor; a second pass over the same day
replaces instead of doubling; and the board reports `configured`, `rows` and `lastDay`.

The rows are tagged `org_id = 'e2e-admin'` and deleted afterwards (`CARDO_E2E_KEEP=1` keeps them for a
screenshot). The poller *container* is not part of this: the Analytics endpoint is pinned in code and
cannot be redirected by design, so the service path is covered by `docker compose --profile admin
config` and the profile test, not by a live call. A live organization key is still the only way to
prove the real Anthropic response ([risks.md](../risks.md) #12).
